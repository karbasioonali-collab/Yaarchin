# Migration 0000 — پایه (کاربر، دسترسی، نشست، تنظیمات، لاگ)

- **وضعیت:** ⏸ پیشنهادی، منتظر تأیید مالک. **هنوز روی هیچ دیتابیسی اجرا نشده.**
- **فایل SQL:** `web/drizzle/0000_foundation.sql`. این فایل خودکار از `web/src/db/schema/` ساخته شده.
- **اجرا بعد از تأیید:** `cd web && npm run db:migrate`

## اصول رعایت‌شده
- کلید اصلی جدول‌ها `uuid` است. استثنا: جدول‌های لاگ و رویداد که فقط ردیف اضافه می‌کنند و `bigserial` دارند.
- همه‌ی زمان‌ها `timestamptz` هستند.
- فیلدهای متغیر در `jsonb` (`meta`، `props`) قرار می‌گیرند تا فیلد جدید به migration نیاز نداشته باشد.
- مقدارهای شبه‌enum (مثل `status`) از نوع `text` هستند، نه `enum` پستگرس، تا اضافه‌کردن مقدار جدید migration نخواهد.
- **هیچ رمز یا توکن خامی ذخیره نمی‌شود:**
  - رمز عبور: هش argon2id.
  - توکن نشست: هش SHA-256.
  - رمز TOTP: رمزشده با AES-256-GCM.
  - کدهای بازیابی: هش.
- لاگ فعالیت و رویدادها فقط ردیف اضافه می‌کنند.

## جدول‌ها (۱۴ جدول)

### کاربر و دسترسی
| جدول | کاربرد | ستون‌های مهم |
|---|---|---|
| `users` | همه‌ی کاربران (ادمین، کارشناس، مشتری، و در فاز ۲ کاربر شرکت) | `full_name`، `mobile` (یکتا)، `email` (یکتا، بدون حساسیت به حروف)، `password_hash`، `status`، `meta` |
| `roles` | نقش‌ها | `key` (admin/expert/customer/company)، `name_fa`، `requires_2fa`، `is_staff` (دسترسی به پنل)، `is_system` (غیرقابل حذف) |
| `permissions` | لیست دسترسی‌ها. در کد تعریف و با seed همگام می‌شود | `key` مثل `companies.edit`، `group_key`، `name_fa` |
| `role_permissions` | اتصال دسترسی به نقش | — |
| `user_roles` | نقش‌های هر کاربر (هر کاربر می‌تواند چند نقش داشته باشد) | `granted_by` |
| `teams`، `team_members` | تیم‌ها. فعلاً `internal`؛ در فاز ۲ تیم هر شرکت | `kind`، `role_in_team` |

### ورود و امنیت
| جدول | کاربرد |
|---|---|
| `sessions` | نشست‌های ورود. `two_factor_verified_at` یعنی مرحله‌ی دوم ورود تأیید شده. `impersonating_user_id` برای وقتی است که ادمین «به‌جای مشتری» می‌بیند. |
| `user_totp` | ورود دومرحله‌ای با اپ Authenticator. `last_used_step` جلوی استفاده‌ی دوباره از یک کد را می‌گیرد. |
| `user_recovery_codes` | کدهای بازیابی یک‌بارمصرف، برای وقتی که گوشی در دسترس نیست. |
| `login_attempts` | ثبت تلاش‌های ورود برای محدودکردن حدس رمز (بر اساس شناسه و IP). |

### سیستم
| جدول | کاربرد |
|---|---|
| `settings` | همه‌ی تنظیمات و سوئیچ‌ها به‌شکل کلید → مقدار JSON. سوئیچ‌ها در گروه `features` هستند (مثلاً `features.payments = false`) و مدل AI هر وظیفه در گروه `ai` (مثلاً `ai.task.customer_chat`). |
| `activity_log` | لاگ فعالیت پنل: چه کسی، چه کاری، روی چه چیزی، مقدار قبل و بعد. اگر ادمین به‌جای کسی کار کرده باشد، ثبت می‌شود. |
| `events` | ثبت رفتار از روز اول: بازدید، کلیک، علاقه‌مندی، پیام و غیره. هم برای کاربر واردشده (`user_id`) و هم ناشناس (`anon_id`). |

## داده‌ی اولیه (seed، بعد از migration)
- **نقش‌ها:**
  - `admin`: پنل، دومرحله‌ای اجباری
  - `expert` (کارشناس): پنل، دومرحله‌ای اجباری
  - `customer`
  - `company`: فاز ۲، بدون استفاده
- **دسترسی‌های مرحله‌ی ۲:** `users.view`، `users.manage`، `roles.manage`، `settings.manage`، `activity.view`، `impersonate`. دسترسی‌های بخش‌های بعدی هم‌زمان با ساخت همان بخش‌ها اضافه می‌شوند.
- **سوئیچ‌ها:** همه‌ی بخش‌های فاز ۱ روشن. پرداخت، پیامک و ایمیل خاموش. `auth.enforce_permissions = false`.
- **اولین ادمین:** با دستور `npm run create-admin` ساخته می‌شود. نام، موبایل و رمز را خودت هنگام اجرا وارد می‌کنی و در کد نیستند.

## تابع مرکزی «کاربر اجازه دارد؟»
- اسم تابع: `can(user, permission, resource?)`، در `web/src/lib/auth/can.ts`. همه‌ی صفحه‌ها و APIها فقط از همین تابع استفاده می‌کنند.
- طبق اصل ۹، فعلاً برای هر کاربر واردشده‌ی پنل «بله» برمی‌گرداند.
- با روشن‌کردن سوئیچ `auth.enforce_permissions`، دسترسی‌های نقش‌ها واقعاً اعمال می‌شوند، بدون تغییر کد یا جدول.
- ورود به پنل از روز اول فقط برای نقش‌های `is_staff` است.

## جدول‌هایی که عمداً در این migration نیستند
دسته‌بندی، شرکت، محصول، داده‌ی خام اکستنشن، قیمت، چت، نرخ‌ها، پروپوزال، پرداخت و پیامک در migrationهای جدا اضافه می‌شوند. هر کدام هم‌زمان با مرحله‌ی خودش ساخته می‌شود و قبلش برای تأیید پیشنهاد داده می‌شود. همه به `users` وصل می‌شوند و این جدول‌ها تغییری نمی‌کنند.
