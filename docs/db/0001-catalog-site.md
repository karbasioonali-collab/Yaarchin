# Migration 0001 — دسته‌بندی، محصول، شرکت، قیمت، محتوای سایت و تماس با ما

- **وضعیت:** ✅ تأیید شد (2026-09-25).
  - روی Postgres محلی سندباکس اجرا و با داده‌ی نمونه تست شد. روی دیتابیسی که فقط ۰۰۰۰ را داشت هم تست شد (همان وضعیت لیارا).
  - **روی لیارا هنوز اجرا نشده.** مالک بعد از استقرار کد اجرا می‌کند (ترتیب پایین).
- **فایل SQL:** `web/drizzle/0001_catalog_site.sql` (خودکار از `web/src/db/schema/catalog.ts` و `site.ts`).
- **نوع تغییر:** فقط افزودنی. ۱۰ جدول جدید؛ هیچ جدول یا ستون موجودی تغییر یا حذف نمی‌شود.
- **برای چه:** فاز ۴ (سایت عمومی) به دسته‌بندی، محصول، عکس، قیمت و محتوای هدر/فوتر/اسلایدر نیاز دارد. همین جدول‌ها پایه‌ی مرحله‌ی ۳ (ایمپورت داده‌ی اکستنشن) هم هستند.
- **اجرا روی لیارا (به همین ترتیب):**
  1. از بخش **بک‌آپ** دیتابیس `yaarchin-db` در پنل لیارا یک بک‌آپ بگیرید.
  2. PR را Merge کنید و صبر کنید تا «Deploy to Liara» در تب Actions سبز شود.
  3. در کنسول برنامه: `npm run db:migrate`، بعد `npm run db:seed` (دو دسترسی تازه)، بعد `npm run db:seed-demo` (داده‌ی نمونه).
  - چرا migrate بعد از استقرار؟ فایل SQL همراه کد جدید می‌رسد و کنسول لیارا همیشه کد در حال اجرا را دارد. تا قبل از migrate، سایت بدون خطا و بدون محصول نمایش داده می‌شود (`docs/infoyaarchin.md` بخش ۱۵).

## جدول‌ها

### کاتالوگ
| جدول | کاربرد | نکته |
|---|---|---|
| `categories` | دسته‌بندی درختی با عمق نامحدود (`parent_id` به خودش) | `slug` لاتین برای آدرس، `sort_order`، `status` (active/hidden)، `image` |
| `companies` | کارخانه/تأمین‌کننده | **محرمانه.** اسم و آدرس فقط اینجاست و در API و صفحه‌ی عمومی خوانده نمی‌شود. `merged_into_id` برای ادغام بدون حذف؛ `user_id` برای فاز ۲ |
| `company_external_ids` | شناسه‌ی شرکت در علی‌بابا و … | یکتا روی (`platform`, `external_id`) برای تشخیص تکراری |
| `company_categories` | دسته‌های هر شرکت | — |
| `products` | صفحه‌ی محصول ترکیبی | `specs` (JSONB: مشخصات مشترک)، `status` (draft/published/archived)، `hs_code` پیشنهادی، `price_unit` |
| `product_listings` | لیستینگ هر شرکت برای محصول (یک صفحه‌ی علی‌بابا) | `moq`، `lead_time_days`، `specs`؛ ممکن است هنوز به محصولی وصل نباشد |
| `product_media` | عکس و ویدیو | `storage_key` (کلید فایل، نه آدرس کامل)، `kind`، `poster_key`، `is_public` (عکس دارای لوگوی کارخانه عمومی نشود) |
| `price_observations` | قیمت‌های مشاهده‌شده | **فقط افزودنی:** قیمت جدید = ردیف جدید، با تاریخ، ارز، پله‌ی تعداد و منبع. `raw_page_id` در مرحله‌ی ۳ به صفحه‌ی خام وصل می‌شود |

### سایت
| جدول | کاربرد |
|---|---|
| `site_blocks` | محتوای ویرایش‌پذیر از پنل، به‌شکل کلید → JSON: `header`، `footer`، `home.slider`، `page.about`، `page.contact`. هر بلوک `is_visible` دارد و هر زیربخش داخل JSON پرچم `visible` خودش را. بخش جدید = کلید جدید، بدون migration |
| `contact_messages` | پیام‌های فرم تماس. `status` (new/read/archived)، `ip` برای جلوگیری از ارسال پشت‌سرهم |

## ستون مشترک `source`
همه‌ی جدول‌های کاتالوگ `source` دارند: `manual` (پنل)، `extension` (ایمپورت)، `demo` (داده‌ی آزمایشی).
داده‌ی نمونه‌ی فاز ۴ با `source = 'demo'` ثبت می‌شود و بعداً با یک دستور کامل پاک می‌شود، بدون دست زدن به داده‌ی واقعی.

## عمداً در این migration نیست (با مرحله‌ی خودش)
- `favorites`، چت، پیام به کارشناس: مرحله‌ی ۵ (ثبت‌نام مشتری).
- `raw_pages`، `extractions`، `category_fields`، `company_notes`، `company_merges`: مرحله‌ی ۳.
- نرخ ارز، HS code، هزینه‌ها: مرحله‌ی ۶. تا آن موقع قیمت تمام‌شده در سایت «به‌زودی» نشان داده می‌شود.

## قیمت در صفحه‌ی محصول چطور حساب می‌شود
- برای هر لیستینگ فعال، آخرین مشاهده‌ی قیمت (هر پله) خوانده می‌شود؛ هیچ ردیفی تغییر نمی‌کند.
- «میانگین» و «بازه» (کمترین تا بیشترین) روی همین آخرین قیمت‌ها و به ارز اصلی (دلار) حساب می‌شود، همراه تعداد کارخانه‌ها و تاریخ آخرین قیمت.
